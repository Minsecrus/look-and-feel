# 直接让用户修改“使用次数”来给常用功能排序

- 相关章节：`order`、`content`、`copy`

## 场景

一款高校校园 App（《我的科大》）的首页顶部有“今日运势”（宜睡觉、忌赶 DDL）和一块“常用功能”区，默认按各功能的使用次数降序排列。开发者没有给它做“编辑模式 + 拖拽排序 + 置顶”组件，而是干脆弹出一张单输入框弹窗，写明：“首页‘常用功能’是根据功能使用次数排序的，若想设置常用功能或调整其顺序，可以手动修改该功能使用次数”，让用户直接把数字改掉（比如给“游戏”填成 `99999` 焊死在首位）。

## 为什么在这里反而有意思

- **把黑盒规则一次讲透（`copy`）**：很多 App 的“智能常用”莫名其妙跳位，用户根本不知道排位依据；这里一句直白说明把底层机制摊在台面上，反而彻底消除了困惑。
- **极低成本解决自定义需求（`order`）**：不用维护“手动置顶”和“按频次自动排序”两套状态机的冲突，一个改数字的弹窗既省研发成本，又能让想微调顺序的人立刻达成目的。
- **契合校园娱乐软件的气质（`content`）**：产品面向的是同校师生，开发者和用户共享一套语境与幽默感；直接暴露计数器、允许“合法改数值”，反而带来一种打破第四面墙的真诚感与玩梗乐趣。

## 为什么商业软件通常不能照抄

- **把底层实现模型甩给了用户**：常规大众软件里，用户的意图是“把某项放前面”，而不是做算术题去凑“A 是 15、B 是 20，所以 C 要填 17”；一旦有人把某项改成 `99999`，后续真实的“按使用次数排序”语义也会被彻底打穿。
- **成立的前提是“主流程靠谱、娱乐只在边缘”**：查课表、看考场这类硬需求依然必须稳妥清晰，这种带点“程序员偷懒与整活”的写法只适合容错率高、不涉及商业风控或严苛效率的校园、社区或极客工具。
